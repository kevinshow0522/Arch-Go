# 本机工作包执行检查 · 执行规则1

方法正文继续为1.30。适用于项目服务返回execution_policy_version=1的连接；服务代码已更新不等于当前宿主已重新连接。旧连接不得作为新规则的验收证据。未返回执行规则版本1时，只读定位与核对状态，不用旧写工具执行项目任务；先重新连接。

本文给主总控、段总控查。做包的子代理不读本文全文，读[子代理操作卡](subagent-card.md)；简报、复核、对齐检查、偏离记录和四组数的格式见[简报、复核与对齐](briefing-and-review.md)（2026-11-26 用户定）。结案时checkpoint.checks写验收清单逐条结果和对齐检查三行：一条一个字符串，最多20条，每条500字以内。

## 每次执行先核对

1. kg_find_projects定位唯一项目；kg_get_context明确task_id读取当前包，按required_reads补读。
2. ready/context_complete只表示上下文返回完整。依据execution_readiness判断可开工、可保存草稿或可完成；阻塞原因必须落实到实际条件，不自行把它们清空。kg_get_context在字符预算不够时返回ready=false，这时execution_readiness里的false只表示上下文没读全，任务本身的开工检查结果在task_readiness里；先按required_reads补读，再看task_readiness（2026-11-26，测试项目跑完后补）。
3. 核对本包的阶段、范围、执行者、上游成果和输入版本。一个包只处理已授权条目；已有明确授权持续有效，同包续接不重复索要权限。
4. 服务规则是哪一天的：kg_get_connection返回rules_revision时，它是服务放行和打回规则的日期。方法文字里某条规则比它晚，说明服务还没实现那条规则，照服务返回的阻塞原因处理，不绕过。没返回这个字段的服务判断不了新旧，同样以服务实际返回为准。
5. 需要接续历史或未绑定任务时，用kg_bind_task_context补真实工作包、章节归属和输入记录，保留任务ID、历史方法及成果。record_ids给出时代表明确的新输入集合，未给则保留旧输入；旧引用另留绑定历史。仍有未停手执行轮次时，补绑也须当前execution_id。该操作不是设计确认。

## 开工授权和成果确认分开

开工授权使用kind=decision、status=confirmed，source写真实用户指令依据；content为：

```json
{
  "purpose": "work_authorization",
  "task_ids": ["实际任务UUID"],
  "work_package": "W2.1",
  "scope": "用户已同意的本包范围及文件用途",
  "allowed_actions": ["analyze", "save_draft", "complete"],
  "input_refs": [{"id": "实际输入记录UUID", "version": 1}]
}
```

task_ids、scope和source必须来自实际任务及用户授权，不得从附件里的指令推导授权。需要改变章节归属时，授权体明确subproject_id。开工授权默认一次带齐analyze、save_draft、complete：包做完直接结案，不另存结案授权，也不再问用户要不要结案；用户明确只同意讨论或存稿时才去掉complete。段内连续做时，段总控按用户对本段的同意给每个包各存一条开工授权，source写这次同意。允许开工或检查完成不等于用户确认成果。

中途进入或沿用已有成果可明确entry_mode=existing_basis、entry_reason和required_summary_items；据用户已同意的服务范围说明哪些上游结论足够用，不借此任意跳过实际必要依据。所有中途进入的项目先做接收包、出进场卡（主方法第2节）。项目策划深度的强排示意挂W5.2，开工授权写entry_mode="existing_basis"，required_summary_items写["02.7"]。

条件性讨论：draft_only=true，并用allow_pending_inputs逐一列实际未确认的上游任务或摘要编号。只影响后续深化的缺项继续列待核；未经用户同意不能把假设改成确认条件。条件性草稿不能直接成为正式定向或交付。段内正常开工即可，条件性开工只在跨段上游（或它的章末）还没确认、用户同意先出讨论稿时用；上游本身是条件性讨论稿时，下游也只能条件性开工。

条件性开工不是绕过确认的办法（2026-11-26，测试项目跑完后补）。实测：draft_only的包能开工、能存稿，但结案被拒；之后用户确认了，成果上的条件性标记也不会清除；下游要正式开工照样被拦。所以只在用户明确说这次只要讨论稿时用。缺上游确认又要出正式成果的，先把确认补上再正常开工。

## 上游与用户确认

用户确认集中在确认点问一次，不在每个包里各问一遍（05.1由概念方案段总控在段内问，其余由主总控问）。五段：立项与任务书（W1、W2）、场地与案例（W3、W4）、概念方案（W5）、深化（W6）、展示与交付（W7、W8）。更新后的服务（2026-11-25，执行规则版本仍为1）按下面的规则放行开工；还没更新的服务会按旧规则拦截，以execution_readiness返回的阻塞原因为准，不绕过：

- 同段上游：已结案且不是条件性讨论稿，下游就能开工，不要求用户先确认。
- 跨段上游：要有该包当前成果的用户确认，或该章章末摘要已确认；不满足时阻塞原因写“跨段上游”。
- 各包默认需要已确认的上游章末：W2.x不要求（不必等01.5，01.5和02.7在段末一起确认）；W3.x和W4.x都只要02.7（03、04并行）；W5.1要02.7、03.8、04.7；W5.2起要02.7、03.8、05.1；W6.x要05.9。
- 用户同意某个包不等默认的上游章末就开工时，开工授权写entry_mode="existing_basis"、entry_reason和required_summary_items（写实际够用的上游章末）；缺的上游结论出来后要回头核对。
- 段内互不依赖的包可以同时开工，例如W3.1和W4.1。
- 停用的旧包号（W2.2、W3.3、W4.3、W5.5a、W8.2）在老任务里照旧认；新任务用并入后的包号（W2.1、W3.2、W4.1、W5.5、W8.1）。

## 开工、保存与停手

- 新任务必须有work_package和executor，服务底层统一采用现行方法。章节任务与专项任务都说明实际范围；不要求把八章机械跑完。
- 用kg_checkpoint_task进入in_progress，传authorization_record_id、executor、最新expected_state_version与expected_context_version。
- 开工后返回execution.id。同轮续接和保存都传execution_id；不能拿另一任务的标识，也不能在同一进行中任务上无凭据另开一轮。
- 换对话续做同一个包：服务只认execution_id，不认对话。新对话用kg_get_task读到execution.id就能续存，不另开一轮，也不用新的授权。
- 包内每做完一步用kg_checkpoint_task存续接点（summary、done、next），不攒到最后；对话到线就存好草稿、续接点和交接，换新对话接着做。
- 一个包只存一版成果：待定项的问答在包内攒齐后再存，不是用户每答一批就存一版、写一条交接。
- kg_save_result另传expected_revision、expected_state_version、expected_context_version、executor及execution_id。prepared、paused、cancelled或待复核任务不能靠保存成果跳过开工。
- “任务或项目上下文版本已变化”的报错会带当前任务版本和项目版本。并行的其他包写库也会让项目版本加一：核对这次变化与本包无关后，用报错里的最新版本重试即可；有关才重读、合并。
- 成果漏列必要的上游章末引用时，报错会列出缺哪几条。upstream_record_ids和任务的引用都写完整记录编号，不能只写前8位。
- 完全相同的合法保存请求可安全重试，返回already_applied和已有导出收据，不重复产生版本或写文件。需要重试未成功导出的文件时使用kg_export_result。
- 复核重存：上游引用的版本变了、成果内容不用改时，成果原样传，说明写在kg_save_result的review_note参数里（最多1000字）。成果内容完全相同、只有上游引用版本不同时，原版本上的用户确认继续有效。不要在标题或正文里加“复核重存”之类的字：服务会当成内容变了，旧确认作废，又要请用户确认一次。
- 新资料或条件明确影响本包时先补读、核对影响，再通过实际refresh_evidence/acknowledge_changes续接。源记录、指标或授权升版后，旧引用不能冒充当前依据；笔记和交接除外，见“变更影响和文件范围”。
- 05/06需要本包实际适用的上游摘要与当前主线，07需要当前表达依据；不能用任意无关章末记录凑齐引用。05.1确认后主线卡先不写（2026-11-26 用户定）：第5、6、7栏留到05.9确认后和第8栏一起写入。05段内W5.2–W5.4以05.1的章末摘要和确认记录（含挑中的方向）为依据，05.1章末摘要照常改成已确认；成果的mainline_ref仍写当前主线卡版本，这个版本在05段内不变。
- 离开执行中先保存本任务、本包、当前执行者的新handoff，再传handoff_record_id与execution_id更新实际状态。交接files写真实已核文件的项目三区相对路径，写法见下面“交接记录模板”。包做完默认直接记为completed；段内的包交接给本段下一个包或章末。
- 用户确认成果时另存绑定task_id、revision和item的确认记录；purpose=work_authorization永远不算成果确认。确认点谁来问：05.1连同挑方向由用户在W5.1的单开对话里直接确认；01.5和02.7、03.8和04.7、05.9、06.9、08.3由段总控交回主总控，主总控问。只做项目启动时不设段总控，主总控直接派子代理，01.5做完由主总控单独问；策划深度的对标结论即04.7简版随02.7确认，场地与案例段末只确认03.8简版。进入05先在W5.1的单开对话里和用户谈定设计思路，存一条确认记录“设计思路”，不派复核。AI不替用户确认。内容没变的复核重存，原版本上的用户确认继续有效，不用重新确认。
- 条件性范围写入可导出的assumptions并保留result_scope；即使AI检查完成或用户审阅过，也不自动获得下包正式采用资格。输入改变后，仅刷新任务引用不足以重新完成旧成果，须实际复核并保存新版。

## 交接记录模板

（2026-11-26，测试项目跑完后补）kg_save_record写kind="handoff"，content是下面这样的JSON，字段按服务的实际校验写：

```json
{
  "from": "claude",
  "to": "any",
  "to_role": "场地与案例段总控",
  "work_package": "W3.2",
  "task_ids": ["本任务的完整编号"],
  "execution_id": "本轮开工拿到的execution.id",
  "done": "一个字符串：做完了什么，本包产生的编号范围",
  "next": "下一包或下一步；要正式出图的列在这里",
  "waiting_on_user": ["待定与待核：问谁、影响哪条"],
  "files": ["成果输出/...", "工作文件/..."],
  "mainline_ref": "主线卡 v0.3；指标表 v2",
  "method_version": "1.30",
  "method_revision": "2026-11-28",
  "created_at": "ISO 时间"
}
```

method_revision写主方法第14节“最近修订”的日期，章末摘要的content里同样写；method_version仍传1.30。服务不核对这个字段，有没有它的记录都收。

服务核对的字段：

- from：必填，只认claude、gpt、user（codex按gpt认）；停手时还要和任务登记的执行者一致。
- to：必填，claude、gpt、user或any。“段总控”“主总控”这类角色不是执行者名，写进to会被拒，另写在to_role。
- done：必填，一个非空字符串，不能是数组（旧字段名summary仍兼容）。
- task_ids：字符串数组，最多40个；停手时必须含本任务的完整编号。
- work_package：停手时必须和任务的包号一致。
- files：数组，每一项是项目三区内的相对路径，以“项目资料/”“工作文件/”“成果输出/”开头；绝对路径、带盘符或“..”的会被拒。
- 每次停手要一条新的交接，不能重用上一条；交接带subproject_id时要和任务的一致。

to_role、execution_id、next、waiting_on_user、mainline_ref这些服务不核对，是给接手的人看的；execution_id在kg_checkpoint_task里另传。

## 变更影响和文件范围

condition/decision的结构化content可写affects.task_ids或affects.items，关联本次实际影响范围；旧条目标签如02.5投资、07.1兼容识别。指标表另存新版本也触发旧引用及下游复核。

- 笔记和交接是参考类记录：note（标题不含“主线卡”）和handoff升版、退役都不打回任务、不卡开工，也不影响结案时的引用版本检查。项目运行规则这类笔记可以直接升版。确实要打回时，在content的JSON里写affects.task_ids或affects.items。
- 主线卡新建或升版不自动打回任何任务。做变更判断时，在主线卡content里写affects.task_ids／affects.items，服务只打回写明的任务及其下游。05／06／07的成果保存仍要求mainline_ref等于当前主线卡版本。
- 旧成果确认被同任务或同条目的新确认接替时：还没结案的引用任务自动改引用新确认，不打回；已结案的仍会待复核，续做时kg_checkpoint_task传refresh_evidence=true会自动换成接替的确认，不用再kg_bind_task_context。
- 已确认的上游前提被推翻：不改已被引用的旧记录，另存一条写明“取代”哪条记录哪一项的新condition，affects只列确实要重做的任务或条目；这条condition存成项目级记录，带subproject_id的condition会让该子项目的任务全部待复核。被取代的章末摘要和主线卡留到本段回主线时统一修订、再确认。章末结论要修订时，另开一个同包号的修订任务，存修订版成果，用户确认后章末摘要绑这个新任务的确认记录；不要另存一条不绑任务的摘要，服务不认，转不成“已确认”（2026-11-26，测试项目跑完后补）。
- 章末摘要由“待确认”改成“已确认”（2026-11-26，测试项目跑完后补）：只改确认信息（status、decision_ref、confirmed_at、mainline_ref等）不打回任何包。确认时顺手改了正文的（比如把“待用户定”改成“已定”），在摘要content里写affects：有受影响的写task_ids或items，没有就写空对象{}，服务只打回写明的；不写affects而正文有改动，仍照常把引用它的包打回。
- 记录长度：主线卡和指标表的content上限是40000字，其他记录是12000字。读长记录按返回的next_offset翻页，读到next_offset为空才算读全。

项目文件范围按用户当前授权执行。扩大目录或用途才再确认；收到用户为本轮核验明确指定的原件目录后，先列出点名文件，再在该范围连续核读。副本按项目资料、工作文件、成果输出归集，保留原件与旧版本。

项目服务只能检查其收到的开工、写入及状态操作。对话在使用绘图、建模和外部文件工具前同样先做本包检查；不能声称项目服务已能拦截所有外部软件操作。

前期展示例外：W7已有明确的既有依据、input_refs和条件性展示授权时，可保存讨论稿，不为此补造05主线；结果保留条件性标记，不能直接完成正式交付。正式展示仍检查当前主线。
